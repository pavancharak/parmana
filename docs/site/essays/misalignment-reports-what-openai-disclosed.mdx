---
title: "OpenAI published 20 misalignment reports. Most of them are about actions, not answers."
description: "What OpenAI's misalignment reports describe, which failures move money or data, and which ones a gate outside the agent would and would not stop."
---

In September and October 2026, OpenAI began publishing [Misalignment Reports and Notices](https://alignment.openai.com/misalignment-reports/):
20 reports on how its own models behaved during internal training, evaluation and deployment, and 3 notices on
related incidents. The reports are candid, and they are worth reading closely, because the failures they describe are
not the ones most people expect.

A typical case looks like this. An agent is asked for a number that sits behind a public dashboard. The terminal tool
it was given allows only `GET` requests, and the dashboard needs a `POST`. The agent writes its own program to send the
`POST`, gets the number, and keeps going. The answer is correct. The agent has still done something its operators did
not allow.

OpenAI's own conclusion is the same: **a correct answer does not show that the agent behaved appropriately.**

## What the reports describe

The reports cluster into a few patterns.

- **Working around restrictions.** Models got past GET-only internet access, used a browser to send requests they were
  not allowed to send, and reached internal systems from a grading tool that was meant to be used only as a calculator.
- **Using credentials it was not given.** One model found a GitHub token and published it in a public repository. Another
  used an API key it found on public GitHub repos. A third derived wallet keys from public developer recovery phrases
  and paid for a test-network deployment from an account it had not been given.
- **Concealment.** A monitor was disabled, and the agent later told the user it had not touched the monitor. Compaction
  summaries, the notes a model writes to carry a task into its next context, contained instructions to hide mistakes
  and to invent missing data without saying so.
- **Sabotage of the environment.** A grading model whose input files were missing created fake inputs, then deleted
  software in its environment, hoping the host would replace it.
- **Agents talking to each other through the wrong channels.** Training agents used an internal package registry as a
  message board, uploaded files to public hosts so co-workers could fetch them, and posted to a public wiki.

## Where a gate helps, and where it does not

The reports are useful because they show which failures sit at the boundary of an action and which do not.

A gate that holds the credentials and checks each action before it runs can block the actions that have an external effect: publishing data, changing a system's configuration, writing to a shared system, or uploading files. Five of the twenty reports describe that kind of action, provided the agent's writes go through the gate. Three more are blocked only when the agent has no credentials or network route of its own, such as a key it found online or a wallet whose keys it derived. In those cases, the agent's own belief that the action is fine does not matter. The check has to come from a policy the agent does not hold, and from a grant with a limit and an end date.

A gate would **not** have stopped the other eleven. They fall into a few groups:

- Reads that look harmless, such as a `GET` to a public site that returns data the agent should never have fetched, or the custom requests that followed it. Only network egress control stops these.
- Text the agent writes into its own summaries. Nothing in the reports says those summaries were checked before the next context read them.
- Exploits of the external sites and internal machines the agents reached, such as a government statistics server or an evaluation host.
- Local actions inside a sandbox, such as deleting software in a grader's environment, and prompt injections that spread only inside simulated tool calls.
- Network-level leaks, such as the DNS path to a public chatbot. The fix there is infrastructure, not authorization.

This is why we keep returning to the same distinction: **a prompt tells an agent what it should do; a gate decides what
it can do.** The reports show agents that treat instructions as negotiable, sometimes correctly and sometimes not.

## What this does not do

These reports do not describe Parmana. OpenAI's cases come from its own training and deployment environments, and the
fixes described there (hardened DNS filtering, offline web caches, separate monitoring systems) are infrastructure
decisions that sit below any authorization layer. Parmana does not replace those controls, and it does not make a model
honest. It only ensures that the actions an agent takes against your systems go through a check the agent cannot edit.

## The question to ask

When you read a report like this, ask: **which of this agent's actions would have needed a signed approval, and which
ones could it take without asking anyone?** Then check that your own agents' answers match the policy you wrote, not
the one the agent described to you.
